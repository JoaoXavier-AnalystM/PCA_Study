1. histogram_quantile() - Latency Percentiles

This is the most complex PromQL function and heavily tested on the exam. It computes percentiles (p50, p90, p99) from the buckets of a Histogram.

Syntax

histogram_quantile(φ, b)

φ = desired percentile (0 to 1). E.g., 0.99 = p99
b = range vector of the buckets with rate() or sum() 

# P99 latency of HTTP requests
histogram_quantile(0.99,
  rate(http_request_duration_seconds_bucket[5m])
)

# P50 and P95 per handler (grouped)
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, handler)
)
# CRITICAL: always keep the "le" label in by() when aggregating!

# P99 summing multiple instances
histogram_quantile(0.99,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
🚫 Fatal error: forgetting the "le" label

When aggregating Histogram buckets, the le (less than or equal) label MUST be included in by(). Without it, all buckets are summed into a single value and the percentile comes out wrong.

✅ sum by (le, job) (rate(duration_bucket[5m]))
❌ sum by (job) (rate(duration_bucket[5m])) ← loses the le!

Why use Histogram instead of Summary for percentiles?

AspectHistogramSummary
Percentile calculationPrometheus serverApplication client
Multi-instance aggregation✅ Possible (sum buckets, then quantile)❌ Impossible
AccuracyApproximate (depends on buckets)Exact (configurable)
Computational costServer (evaluation)Client (collection)
Quantile flexibilityAny quantile after the factOnly pre-defined quantiles

2. Binary Operators with Vector Matching

When operating on two vectors with different labels, we need to specify how to match them.

on() and ignoring() - Controlling which labels are used for the match

# Error: the metrics have different labels
method_code:http_errors:rate5m{method="get", code="500"} 24
method:http_requests:rate5m{method="get"}               600

# on() - uses ONLY the listed labels for the match
method_code:http_errors:rate5m
/ on(method)
method:http_requests:rate5m

# ignoring() - IGNORES the listed labels in the match
method_code:http_errors:rate5m
/ ignoring(code)
method:http_requests:rate5m

group_left() and group_right() - Many-to-One Joins

When one side has more series than the other, we need to specify which side "wins":

# Left group has more series (many-to-one)
# group_left() = the left side can have many series for each series on the right
metric_with_many{} * on(job) group_left(env) metric_with_env{}

# group_left(env) also COPIES the "env" label from the right side to the result
# Useful for enriching metrics with metadata from another metric

# Real example: adding cluster info to the pod metric
container_cpu_usage{pod="api-1"} * on(pod) group_left(cluster) pod_info{pod="api-1", cluster="prod"}

group_left(): the left side can have many series for 1 on the right
group_right(): the right side can have many series for 1 on the left
The labels inside the parentheses are extra labels to copy from the other side.

3. predict_linear() - Predictive Alerts

Projects the future value of a gauge using linear regression over recent history.

Syntax

predict_linear(v range-vector, t scalar)

v = series with history for the projection
t = how many seconds into the future to project 

# Alert if the disk will fill up in less than 4 hours
# Using 1h of history to project 4h into the future
predict_linear(node_filesystem_avail_bytes[1h], 4 * 3600) < 0

# If it will fill up in less than 2 hours (using 30min of history)
predict_linear(node_filesystem_avail_bytes[30m], 2 * 3600) < 0

# Estimate when memory will run out
predict_linear(node_memory_MemAvailable_bytes[2h], 6 * 3600) < 0
💡 How to interpret

If predict_linear(...) < 0, the linear projection indicates the value will reach zero (or go negative) before time T. For disk: available space reaching zero = disk full.

4. absent() - Alerting When Metrics Disappear

Returns a vector with value 1 if the expression produces no series. Essential for "absence alerts".

# Alert if the "api" job is not reporting metrics
absent(up{job="api"})
# Returns: vector{job="api"} = 1 (if absent), nothing (if present)

# Alert if there are no up targets in the job
absent(up{job="api"} == 1)

# Alert if a specific metric disappears
absent(http_requests_total{env="production"})

# Combine with for in an alerting rule to avoid false positives
# alert: JobMissing
# expr: absent(up{job="api"})
# for: 5m

absent() returns a vector with labels derived from the selector when absent. If the series exists, it returns an empty vector (no data). To use it in alerts, combine it with for: to avoid firing on a temporarily failed scrape.

# Creates the "short_instance" label by stripping the port from "instance"
label_replace(
  up,
  "short_instance",   # destination label
  "$1",               # value (regex capture)
  "instance",         # source label
  "(.+):.*"           # regex (captures host, drops :port)
)

6. Recording Rules - Precomputing Queries

Recording Rules evaluate a PromQL expression at regular intervals and store the result as a new metric. Essential for heavy queries used across several dashboards/alerts.

Recording Rules file structure

# rules/recording.yml
groups:
  - name: http_rules          # Group name
    interval: 1m              # Optional: overrides the evaluation_interval
    rules:
      - record: job:http_requests:rate5m      # Name of the resulting metric
        expr: |
          sum by (job) (
            rate(http_requests_total[5m])
          )

      - record: job:http_error_rate:ratio5m
        expr: |
          sum(rate(http_requests_total{status=~"5.."}[5m])) by (job)
          /
          sum(rate(http_requests_total[5m])) by (job)

Naming Convention for Recording Rules

Format
level:metric:operations
level
Aggregation level. E.g., job, instance, cluster
metric
Base metric. E.g., http_requests
operations
Operations applied. E.g., rate5m, ratio, sum
# Correct name examples:
job:http_requests:rate5m        # request rate per job, 5m window
job:http_error_rate:ratio5m     # error ratio per job, 5m
instance:cpu_usage:avg5m        # average cpu per instance, 5m
cluster:http_requests:sum       # sum of requests per cluster

When to use Recording Rules?

  • Queries used across multiple dashboards (avoid reprocessing)
  • Computationally heavy queries (histogram_quantile with many buckets)
  • Base queries for alerting rules (precompute for faster alerts)
  • Create derived metrics that combine multiple raw metrics

Configuring Prometheus to load the rules

# prometheus.yml
rule_files:
  - "rules/*.yml"
  - "/etc/prometheus/rules.yml"

7. Subqueries - Queries within Queries

# Syntax: expr[range:resolution]
# range = subquery window
# resolution = evaluation frequency

# Maximum rate per hour, evaluated every 1 minute
max_over_time(rate(http_requests_total[5m])[1h:1m])

# Detect if the rate was above 100 at any point in the last hour
max_over_time(
  rate(http_requests_total[5m])[1h:5m]
) > 100

Subqueries are computationally expensive. Use them sparingly and prefer Recording Rules for recurring cases.

Review Questions

Q1. What is the correct query for computing the 99th latency percentile using a Histogram?
A) quantile(0.99, http_request_duration_seconds)
B) histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
C) histogram_quantile(99, rate(http_request_duration_seconds_bucket[5m]))
D) p99(http_request_duration_seconds[5m])
✅ Answer: B
histogram_quantile(φ, b) - φ is the quantile between 0 and 1 (not 0-100!), and b must be the buckets with rate(). It uses the _bucket suffix, not the base metric.
Q2. When aggregating Histogram buckets with sum() for use in histogram_quantile(), which label must you keep?
A) job
B) instance
C) le
D) handler
✅ Answer: C
The "le" (less than or equal) label defines each bucket's upper bound. Without it, histogram_quantile() cannot identify the buckets and the calculation comes out wrong. Always: sum by (le, ...) when aggregating buckets.
Q3. What does the query predict_linear(node_filesystem_avail_bytes[1h], 4*3600) < 0 do?
A) Alerts if the disk has less than 4 hours of uptime
B) Computes the average free space over the last hour
C) Alerts if, based on the last hour's trend, the disk will fill up in less than 4 hours
D) Checks if the disk filled up in the last 4 seconds
✅ Answer: C
predict_linear(v, t) projects the value of v t seconds from now. If the projection is negative, the available space will reach zero before t. 4*3600 = 4 hours in seconds.
Q4. What does absent(up{job="api"}) return when the "api" job is being monitored normally?
A) 0 (zero)
B) 1 (one)
C) An empty vector (no data)
D) The current value of the up metric for the api job
✅ Answer: C
absent() returns a vector with value 1 only if the series does NOT exist. If the series exists (the job is monitored), absent() returns an empty vector - no data. This means: the alerting rule does not fire when the job exists.
Q5. What is the correct naming format for a Recording Rule that computes the HTTP request rate per job?
A) http_requests_rate_5m_by_job
B) job:http_requests:rate5m
C) job_http_requests_rate5m
D) recording:http_requests_total:rate
✅ Answer: B
The convention is level:metric:operations. "job" = aggregation level, "http_requests" = base metric, "rate5m" = operation applied with a window. It makes the series easy to identify and avoids conflicts.
Q6. What is the group_left() operator for in PromQL?
A) To aggregate series on the left side of the query
B) For many-to-one joins where the left side has more series, allowing extra labels to be copied from the right side
C) To filter series based on the left side's labels
D) To sort the result by the left column
✅ Answer: B
group_left() allows many-to-one joins: many series on the left can link to one on the right. The labels inside group_left()'s parentheses are copied from the right side to enrich the left result.
Q7. Which of the following statements about Recording Rules is INCORRECT?
A) Recording Rules are stored as new metrics in the TSDB
B) Recording Rules improve the performance of repeated queries
C) Recording Rules are evaluated in real time only when a dashboard queries them
D) Recording Rules follow the level:metric:operations naming convention
✅ Answer: C
INCORRECT: Recording Rules are evaluated periodically (per evaluation_interval) and stored in the TSDB, regardless of whether anything queries them. When a dashboard queries them, the data is already precomputed - which is why they are faster.
Q8. Which function should be used to create an alert when a metric's value changed more than 3 times in the last hour?
A) rate(config_version[1h]) > 3
B) changes(config_version[1h]) > 3
C) increase(config_version[1h]) > 3
D) delta(config_version[1h]) > 3
✅ Answer: B
changes() counts how many times a series' value changed over the specified period. Ideal for detecting configs that changed unexpectedly many times. rate() would be for an increasing counter; increase() would be for the amount grown.
