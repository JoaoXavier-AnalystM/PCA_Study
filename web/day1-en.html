1. The Three Pillars of Observability

Observability is the ability to understand a system's internal state from its external outputs. The three pillars are complementary, not substitutes.

PillarWhat it isFormatBest forExample
MetricsNumeric values aggregated over timeTime seriesAlerts, dashboards, SLOsCPU: 72%, Req/s: 1.200
LogsDiscrete events with textual contextStructured text lineDebugging, auditing[ERROR] DB timeout after 5s
TracesEnd-to-end request trackingNested spansMicroservice performancereq→auth(12ms)→db(45ms)
💡 Exam Tip
"A slow request crossing 5 microservices" → Tracing. "Error rate over the last 5min" → Metrics. "A specific error message" → Logs.

2. SLI, SLO and SLA

Definitions

SLI - Indicator
The actual metric being measured. E.g., availability = requisições_ok / total
SLO - Objective
The team's internal target. E.g., SLI ≥ 99.9% for the month
SLA - Agreement
Formal contract with the client, with penalties. E.g., SLA 99.5%
Error Budget
100% − SLO = allowed error margin. If SLO=99.9% → budget = 0.1%

Practical hierarchy

SLA < SLO < 100%

The SLO must be stricter than the SLA - that way you have room to fix problems before violating the client contract.

E.g., SLA = 99.5% / SLO = 99.9% / monthly Error Budget = ~4.4h

Error budget exhausted → the team stops shipping features and focuses on reliability (Google's SRE practice).

3. Push vs Pull - Collecting Metrics

How it worksPrometheus schedules and scrapes /metrics from each targetApplication pushes metrics to the Pushgateway

DiscoveryAutomatic service discoveryRequires manual push
EndpointGET /metricsPUT /metrics/job/{nome}
⚠️ Beware of the Pushgateway
The Pushgateway persists metrics indefinitely after the job finishes. To clean up: DELETE /metrics/job/{job_name}. It is not an event bus - it is a metrics cache.

4. Prometheus Architecture

The Prometheus ecosystem is made up of distinct components with well-defined responsibilities:

Prometheus Server
Central engine: scraping, TSDB, rule evaluation. Port :9090
TSDB
Local, optimized Time Series Database. Default retention: 15 days
Exporters
Adapters that expose metrics from external systems in the Prometheus format
Pushgateway
Buffer for batch jobs. Port :9091
Alertmanager
Processes alerts: dedup, grouping, routing, silences. Port :9093
Grafana
Visualization via PromQL. Port :3000
Node Exporter
Host metrics (CPU, RAM, disk, network). Port :9100
Port Mnemonic - Essential for the Exam

9090 = Prometheus (P is the 16th letter → 9+0+9+0=18, forget that, just memorize it!)
9091 = Pushgateway (Push comes after P → +1)
9093 = Alertmanager (Alert → +3)
9100 = Node Exporter (100 nodes)
3000 = Grafana (G → 3 letters before... just memorize: 3000)

6. Data Model - Time Series, Labels and Samples

Structure of a Time Series

<metric_name>{<label_name>=<label_value>, ...} <value> [<timestamp>]

# Full example:
http_requests_total{job="api", instance="10.0.0.1:8080", method="GET", status="200"} 1024 1620000000000
Metric name
Identifies what is being measured. E.g., http_requests_total
Labels
Key=value pairs that differentiate instances. Each unique combination = 1 time series
Sample
A (timestamp, float64) pair - the actual data point
Cardinality
Total number of unique time series. High cardinality = performance problem
🚫 High Cardinality Labels - Never do this
Never use as labels: user_id, request_id, session_id, email, user IP
This creates millions of time series → collapses the TSDB. Use logs for high-cardinality data.

Naming Convention

Format
namespace_subsystem_name_unit in snake_case
_total suffix
Counters - e.g., http_requests_total
_seconds suffix
Duration - e.g., http_request_duration_seconds
_bytes suffix
Size - e.g., http_response_size_bytes
_ratio suffix
Ratio 0-1 - e.g., disk_usage_ratio

7. Metric Exposition Format

Prometheus reads metrics in a plain-text format (exposition format). Each line is a time series:

# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1234
http_requests_total{method="POST",status="500"} 7

# HELP memory_usage_bytes Current memory usage
# TYPE memory_usage_bytes gauge
memory_usage_bytes 536870912

# HELP http_request_duration_seconds Request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 100
http_request_duration_seconds_bucket{le="+Inf"} 120
http_request_duration_seconds_sum 9.5
http_request_duration_seconds_count 120
Format rules: # HELP = human-readable description. # TYPE = declares the type. Lines without # are samples. The default endpoint is /metrics over HTTP GET.

9. Service Discovery - Overview

Prometheus can discover targets automatically without manually editing the configuration file:

static_configs
Manual list of targets in prometheus.yml. For simple environments.
kubernetes_sd_configs
Automatically discovers Kubernetes pods, services, nodes and endpoints
consul_sd_configs
Integrates with Consul Service Registry
ec2_sd_configs
Discovers EC2 instances via the AWS API
file_sd_configs
Reads targets from a JSON/YAML file - reloads dynamically

Basic prometheus.yml example

global:
  scrape_interval: 15s        # Scrape frequency
  evaluation_interval: 15s    # Rule evaluation frequency

scrape_configs:
  - job_name: 'prometheus'    # Job name (automatic label)
    static_configs:
      - targets: ['localhost:9090']

  - job_name: 'node'
    static_configs:
      - targets: ['server1:9100', 'server2:9100']
    labels:
      env: production          # Extra labels for all targets

Q1. Which observability pillar is best for tracking a slow request crossing 6 microservices?
A) Metrics - because they are more efficient for latency analysis
B) Logs - since each service records the event with a timestamp
C) Traces (distributed tracing) with spans
D) Alerts - because they identify the problem automatically
✅ Answer: C
Distributed tracing with spans is exactly built for this scenario: tracking the full path of a request across multiple services, showing where the bottleneck happened. Tools: Jaeger, Zipkin, OpenTelemetry.
Q2. A company has a 99.9% monthly availability SLO. How much downtime is allowed?
A) 0 minutes - 99.9% basically means always available
B) Approximately 43.8 minutes per month (0.1% of the time)
C) Exactly 1 hour per month
D) It depends on the SLA with the client
✅ Answer: B
Error budget = 100% − 99.9% = 0.1%. In a 30-day month = 43,200 minutes × 0.001 = ~43.2 minutes. This is the "error budget" available before violating the SLO.
Q3. Why does Prometheus use the Pull model instead of Push by default?
A) Pull is more secure because the firewall does not need to allow inbound connections
B) Pull lets Prometheus control the frequency and detect down targets (up=0)
C) Push is not supported in any situation in Prometheus
D) Pull is more network-efficient
✅ Answer: B
With Pull, Prometheus controls the scrape timing and knows exactly when a target stopped responding (producing up=0). With Push, if the agent stops sending, there is no simple way to tell whether it was intentional or a failure.
Q4. Which metric type is correct for measuring the current number of open connections to a database?
A) Counter - because it counts the number of connections
B) Summary - to calculate connection percentiles
C) Gauge - because the value goes up and down as connections open and close
D) Histogram - to distribute connections over time ranges
✅ Answer: C
Gauge is for values that go up AND down. Active connections increase when new connections are established and decrease when they close. Counter only goes up - it would be right for "total connections ever opened".
Q5. What is the main advantage of Histogram over Summary for measuring latency?
A) Histogram is more accurate - it computes exact percentiles
B) Histogram allows aggregation across multiple instances via histogram_quantile()
C) Histogram uses less memory than Summary
D) Summary does not support percentiles above p90
✅ Answer: B
Histogram stores buckets in Prometheus and computes percentiles on the server - which is why you can aggregate buckets from multiple instances before computing the quantile. Summary computes percentiles in the application client, making later aggregation impossible.
Q6. Which label would be problematic to use on a Prometheus metric?
A) method="GET"
B) status_code="200"
C) user_id="usr_abc123"
D) region="us-east-1"
✅ Answer: C
user_id has very high cardinality - it can have millions of unique values. Each label combination = 1 time series. That would create millions of series, overloading the TSDB. Labels should have low, predictable cardinality.
Q7. A batch job finishes in 10 seconds, but the scrape_interval is 15s. Which solution should you use?
A) Reduce the scrape_interval to 5s
B) Use the Pushgateway - the job pushes before finishing
C) Add a 5s sleep at the end of the job
D) It is not possible to monitor short-lived jobs with Prometheus
✅ Answer: B
The Pushgateway exists exactly for batch jobs that finish before the next scrape. The job pushes its metrics (status, duration, result) to the Pushgateway, which stays available for Prometheus to scrape indefinitely.
Q8. What is Prometheus's main configuration file, and which field defines the default scrape interval?
A) config.yaml, the interval field
B) prometheus.yml, the scrape_interval field inside global:
C) prometheus.conf, the collection_interval field
D) prometheus.yml, the evaluation_interval field
✅ Answer: B
The file is prometheus.yml. The scrape_interval field inside global: defines the default collection interval. evaluation_interval defines how often the RULES (alerting/recording) are evaluated - different from scraping!
