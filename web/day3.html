1. histogram_quantile() — Percentis de Latência

Esta é a função mais complexa do PromQL e muito cobrada na prova. Permite calcular percentis (p50, p90, p99) a partir dos buckets de um Histogram.

Sintaxe

histogram_quantile(φ, b)

φ = percentil desejado (0 a 1). Ex: 0.99 = p99
b = range vector dos buckets com rate() ou sum() 

# P99 de latência das requisições HTTP
histogram_quantile(0.99,
  rate(http_request_duration_seconds_bucket[5m])
)

# P50 e P95 por handler (agrupado)
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, handler)
)
# CRÍTICO: sempre mantenha o label "le" no by() ao agregar!

# P99 somando múltiplas instâncias
histogram_quantile(0.99,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
🚫 Erro fatal: esquecer o label "le"

Ao agregar buckets de Histogram, o label le (less than or equal) DEVE ser incluído no by(). Sem ele, todos os buckets são somados num único valor e o percentil fica incorreto.

✅ sum by (le, job) (rate(duration_bucket[5m]))
❌ sum by (job) (rate(duration_bucket[5m])) ← perde o le!

Por que usar Histogram em vez de Summary para percentis?

AspectoHistogramSummary
Cálculo do percentilServidor PrometheusCliente da aplicação
Agregação multi-instância✅ Possível (some buckets, then quantile)❌ Impossível
PrecisãoAproximada (depende dos buckets)Exata (configurável)

2. Operadores Binários com Vector Matching

Quando operamos sobre dois vetores com labels diferentes, precisamos especificar como fazer o match.

on() e ignoring() — Controlando quais labels usar no match

# Erro: as métricas têm labels diferentes
method_code:http_errors:rate5m{method="get", code="500"} 24
method:http_requests:rate5m{method="get"}               600

# on() — usa APENAS os labels listados para fazer o match
method_code:http_errors:rate5m
/ on(method)
method:http_requests:rate5m

# ignoring() — IGNORA os labels listados no match
method_code:http_errors:rate5m
/ ignoring(code)
method:http_requests:rate5m

group_left() e group_right() — Joins Many-to-One

Quando um lado tem mais séries que o outro, precisamos especificar qual lado "domina":

# Grupo à esquerda tem mais séries (many-to-one)
# group_left() = o lado esquerdo pode ter muitas séries para cada série do direito
metric_with_many{} * on(job) group_left(env) metric_with_env{}

# group_left(env) também COPIA o label "env" do lado direito para o resultado
# Útil para enriquecer métricas com metadata de outro metric

# Exemplo real: adicionar info de cluster à métrica de pod
container_cpu_usage{pod="api-1"} * on(pod) group_left(cluster) pod_info{pod="api-1", cluster="prod"}

group_left(): o lado esquerdo pode ter muitas séries para 1 do direito
group_right(): o lado direito pode ter muitas séries para 1 do esquerdo
Os labels dentro dos parênteses são labels extras a copiar do outro lado.

3. predict_linear() — Alertas Preditivos

Projeta o valor futuro de um gauge usando regressão linear sobre o histórico recente.

Sintaxe

predict_linear(v range-vector, t scalar)

v = série com histórico para projeção
t = quantos segundos no futuro projetar 

# Alerta se o disco vai encher em menos de 4 horas
# Usando 1h de histórico para projetar 4h no futuro
predict_linear(node_filesystem_avail_bytes[1h], 4 * 3600) < 0

# Se vai encher em menos de 2 horas (usando 30min de histórico)
predict_linear(node_filesystem_avail_bytes[30m], 2 * 3600) < 0

# Estimar quando a memória vai acabar
predict_linear(node_memory_MemAvailable_bytes[2h], 6 * 3600) < 0
💡 Como interpretar

Se predict_linear(...) < 0, significa que a projeção linear indica que o valor chegará a zero (ou negativo) antes do tempo T. Para disco: espaço disponível chega a zero = disco cheio.

4. absent() — Alertar Quando Métricas Somem

Retorna um vetor com valor 1 se a expressão não produz nenhuma série. Essencial para "alerta de ausência".

# Alerta se o job "api" não estiver reportando métricas
absent(up{job="api"})
# Retorna: vetor{job="api"} = 1 (se ausente), nada (se presente)

# Alerta se não há nenhum target up no job
absent(up{job="api"} == 1)

# Alerta se uma métrica específica some
absent(http_requests_total{env="production"})

# Combinar com for em alerting rule para evitar falsos positivos
# alert: JobMissing
# expr: absent(up{job="api"})
# for: 5m

absent() retorna um vetor com labels derivados do seletor quando ausente. Se a série existe, retorna um vetor vazio (sem dados). Para usar em alertas, combine com for: para evitar disparo por scrape temporariamente falhado.

6. Recording Rules — Pré-computação de Queries

Recording Rules avaliam uma expressão PromQL em intervalos regulares e armazenam o resultado como uma nova métrica. Essencial para queries pesadas usadas em vários dashboards/alertas.

Estrutura do arquivo de Recording Rules

# rules/recording.yml
groups:
  - name: http_rules          # Nome do grupo
    interval: 1m              # Opcional: override do evaluation_interval
    rules:
      - record: job:http_requests:rate5m      # Nome da métrica resultante
        expr: |
          sum by (job) (
            rate(http_requests_total[5m])
          )

      - record: job:http_error_rate:ratio5m
        expr: |
          sum(rate(http_requests_total{status=~"5.."}[5m])) by (job)
          /
          sum(rate(http_requests_total[5m])) by (job)

Naming Convention para Recording Rules

Formato
level:metric:operations
level
Nível de agregação. Ex: job, instance, cluster
metric
Métrica base. Ex: http_requests
operations
Operações aplicadas. Ex: rate5m, ratio, sum
# Exemplos corretos de nomes:
job:http_requests:rate5m        # taxa de req por job, janela 5m
job:http_error_rate:ratio5m     # ratio de erros por job, 5m
instance:cpu_usage:avg5m        # cpu médio por instance, 5m
cluster:http_requests:sum       # soma de requests por cluster

Quando usar Recording Rules?

  • Queries usadas em múltiplos dashboards (evitar reprocessamento)
  • Queries computacionalmente pesadas (histogram_quantile com muitos buckets)
  • Queries base para alerting rules (pré-computar para alertas mais rápidos)
  • Criar métricas derivadas que combinam múltiplas métricas brutas

Configurar o Prometheus para carregar as regras

# prometheus.yml
rule_files:
  - "rules/*.yml"
  - "/etc/prometheus/rules.yml"

7. Subqueries — Queries dentro de Queries

# Sintaxe: expr[range:resolution]
# range = janela do subquery
# resolution = frequência de avaliação

# Máximo da taxa por hora, avaliado a cada 1 minuto
max_over_time(rate(http_requests_total[5m])[1h:1m])

# Detectar se a taxa esteve acima de 100 em algum momento na última hora
max_over_time(
  rate(http_requests_total[5m])[1h:5m]
) > 100

Subqueries são computacionalmente caras. Use com moderação e prefira Recording Rules para casos recorrentes.

Questões de Revisão

Q1. Qual é a query correta para calcular o percentil 99 de latência usando um Histogram?
A) quantile(0.99, http_request_duration_seconds)
B) histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
C) histogram_quantile(99, rate(http_request_duration_seconds_bucket[5m]))
D) p99(http_request_duration_seconds[5m])
✅ Resposta: B
histogram_quantile(φ, b) — φ é o quantil entre 0 e 1 (não 0-100!), e b deve ser os buckets com rate(). Usa _bucket como sufixo, não a métrica base.
Q2. Ao agregar buckets de Histogram com sum() para usar em histogram_quantile(), qual label é obrigatório manter?
A) job
B) instance
C) le
D) handler
✅ Resposta: C
O label "le" (less than or equal) define os limites de cada bucket. Sem ele, histogram_quantile() não consegue identificar os buckets e o cálculo fica incorreto. Sempre: sum by (le, ...) ao agregar buckets.
Q3. O que faz a query: predict_linear(node_filesystem_avail_bytes[1h], 4*3600) < 0?
A) Alerta se o disco está com menos de 4 horas de uptime
B) Calcula a média de espaço livre na última hora
C) Alerta se, com base na tendência da última hora, o disco vai encher em menos de 4 horas
D) Verifica se o disco ficou cheio nos últimos 4 segundos
✅ Resposta: C
predict_linear(v, t) projeta o valor de v daqui a t segundos. Se a projeção é negativa, significa que o espaço disponível chegará a zero antes de t. 4*3600 = 4 horas em segundos.
Q4. O que absent(up{job="api"}) retorna quando o job "api" está sendo monitorado normalmente?
A) 0 (zero)
B) 1 (um)
C) Um vetor vazio (sem dados)
D) O valor atual da métrica up para o job api
✅ Resposta: C
absent() retorna um vetor com valor 1 apenas se a série NÃO existe. Se a série existe (job está monitorado), absent() retorna um vetor vazio — nenhum dado. Isso significa: a alerting rule não dispara quando o job existe.
Q5. Qual é o formato de naming correto para uma Recording Rule que calcula a taxa de requisições HTTP por job?
A) http_requests_rate_5m_by_job
B) job:http_requests:rate5m
C) job_http_requests_rate5m
D) recording:http_requests_total:rate
✅ Resposta: B
A convenção é level:metric:operations. "job" = nível de agregação, "http_requests" = métrica base, "rate5m" = operação aplicada com janela. Isso facilita identificar a série e evitar conflitos.
Q6. Para que serve o operador group_left() em PromQL?
A) Para agregar séries do lado esquerdo da query
B) Para joins many-to-one onde o lado esquerdo tem mais séries, permitindo copiar labels extras do lado direito
C) Para filtrar séries com base nos labels do lado esquerdo
D) Para ordenar o resultado pela coluna da esquerda
✅ Resposta: B
group_left() permite joins many-to-one: muitas séries do esquerdo podem se ligar a uma do direito. Os labels dentro dos parênteses de group_left() são copiados do lado direito para enriquecer o resultado esquerdo.
Q7. Qual das seguintes afirmações sobre Recording Rules está INCORRETA?
A) Recording Rules são armazenadas como novas métricas no TSDB
B) Recording Rules melhoram a performance de queries repetidas
C) Recording Rules são avaliadas em tempo real apenas quando um dashboard as consulta
D) Recording Rules seguem a naming convention level:metric:operations
✅ Resposta: C
INCORRETA: Recording Rules são avaliadas periodicamente (conforme evaluation_interval) e armazenadas no TSDB, independente de haver consultas. Quando um dashboard as consulta, os dados já estão pré-calculados — por isso são mais rápidas.
Q8. Qual função deve ser usada para criar um alerta quando o campo de uma métrica sofreu mais de 3 mudanças na última hora?
A) rate(config_version[1h]) > 3
B) changes(config_version[1h]) > 3
C) increase(config_version[1h]) > 3
D) delta(config_version[1h]) > 3
✅ Resposta: B
changes() conta quantas vezes o valor de uma série mudou no período especificado. Ideal para detectar configurações que mudaram inesperadamente muitas vezes. rate() seria para contador crescente; increase() seria para o total crescido.
