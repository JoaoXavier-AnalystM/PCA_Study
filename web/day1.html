1. Os Três Pilares da Observabilidade

Observabilidade é a capacidade de entender o estado interno de um sistema a partir de suas saídas externas. Os três pilares são complementares — não substitutos.

PilarO que éFormatoMelhor paraExemplo
MétricasValores numéricos agregados no tempoSérie temporalAlertas, dashboards, SLOsCPU: 72%, Req/s: 1.200
LogsEventos discretos com contexto textualLinha de texto estruturadaDebugging, auditoria[ERROR] DB timeout after 5s
TracesRastreamento de requisição ponta a pontaSpans aninhadosPerformance de microsserviçosreq→auth(12ms)→db(45ms)
💡 Dica de Prova
"Uma requisição lenta atravessando 5 microsserviços" → Tracing. "Taxa de erros nos últimos 5min" → Métricas. "Mensagem de erro específica" → Logs.

2. SLI, SLO e SLA

Definições

SLI — Indicator
Métrica real medida. Ex: disponibilidade = requisições_ok / total
SLO — Objective
Meta interna do time. Ex: SLI ≥ 99,9% no mês
SLA — Agreement
Contrato formal com o cliente com penalidades. Ex: SLA 99,5%
Error Budget
100% − SLO = margem de erros permitida. Se SLO=99,9% → budget = 0,1%

Hierarquia prática

SLA < SLO < 100%

O SLO deve ser mais restrito que o SLA — assim você tem margem para resolver problemas antes de violar o contrato com o cliente.

Ex: SLA = 99,5% / SLO = 99,9% / Error Budget mensal = ~4,4h

Error Budget esgotado → time para de lançar features e foca em confiabilidade (prática SRE do Google).

3. Push vs Pull — Coleta de Métricas

AspectoPull (padrão Prometheus)Push (Pushgateway)
Como funcionaPrometheus agenda e scrapa /metrics de cada targetAplicação envia métricas pro Pushgateway
FrequênciaControlada pelo Prometheus (scrape_interval)Controlada pela aplicação
Uso idealServiços de longa duraçãoBatch jobs de curta duração
DescobertaService discovery automáticoRequer push manual
EndpointGET /metricsPUT /metrics/job/{nome}
⚠️ Cuidado com o Pushgateway
O Pushgateway persiste métricas indefinidamente após o job terminar. Para limpar: DELETE /metrics/job/{job_name}. Não é um evento bus — é um cache de métricas.

4. Arquitetura do Prometheus

O ecossistema Prometheus é composto por componentes distintos com responsabilidades bem definidas:

Prometheus Server
Motor central: scrape, TSDB, avalia regras. Porta :9090
TSDB
Time Series Database local, otimizado. Retenção padrão: 15 dias
Exporters
Adaptadores que expõem métricas de sistemas externos no formato Prometheus
Pushgateway
Buffer para batch jobs. Porta :9091
Alertmanager
Processa alertas: dedup, grouping, routing, silences. Porta :9093
Grafana
Visualização via PromQL. Porta :3000
Node Exporter
Métricas de host (CPU, RAM, disco, rede). Porta :9100
🔑 Mnemônico das Portas — Essencial para Prova

9090 = Prometheus (P é a 16ª letra → 9+0+9+0=18, esqueça isso, decore!)
9091 = Pushgateway (Push vem depois de P → +1)
9093 = Alertmanager (Alert → +3)
9100 = Node Exporter (100 nodes)
3000 = Grafana (G → 3 letras antes de... só decore: 3000)

TipoComportamentoSufixoFunção PromQLExemplos de uso

Histogram vs Summary — Diferença Crucial

Cálculo do percentil
Histogram: servidor (Prometheus)
Summary: cliente (aplicação)
Agregação multi-instância
Histogram: ✅ possível
Summary: ❌ não possível
Precisão
Histogram: depende dos buckets
Summary: exata
Recomendado
Histogram na maioria dos casos

Séries geradas pelo Histogram

# http_request_duration_seconds
http_request_duration_seconds_bucket{le="0.1"} 24
http_request_duration_seconds_bucket{le="0.5"} 30
http_request_duration_seconds_bucket{le="1"}   31
http_request_duration_seconds_bucket{le="+Inf"} 31
http_request_duration_seconds_sum   13.2
http_request_duration_seconds_count 31

le = "less than or equal" — todos os buckets são cumulativos!

6. Data Model — Time Series, Labels e Samples

Estrutura de uma Time Series

<metric_name>{<label_name>=<label_value>, ...} <value> [<timestamp>]

# Exemplo completo:
http_requests_total{job="api", instance="10.0.0.1:8080", method="GET", status="200"} 1024 1620000000000
Metric name
Identifica o que está sendo medido. Ex: http_requests_total
Labels
Pares chave=valor que diferenciam instâncias. Cada combinação única = 1 time series
Sample
Par (timestamp, float64) — é o dado em si
Cardinality
Total de time series únicas. Alta cardinality = problema de performance
🚫 Labels de Alta Cardinality — Nunca faça isso
Jamais use como label: user_id, request_id, session_id, email, IP de usuário
Isso cria milhões de time series → colapsa o TSDB. Use logs para dados de alta cardinality.

Naming Convention

Formato
namespace_subsystem_name_unit em snake_case
Sufixo _total
Counters — ex: http_requests_total
Sufixo _seconds
Duração — ex: http_request_duration_seconds
Sufixo _bytes
Tamanho — ex: http_response_size_bytes
Sufixo _ratio
Proporção 0-1 — ex: disk_usage_ratio

7. Formato de Exposição de Métricas

O Prometheus lê métricas em formato texto simples (exposition format). Cada linha é uma time series:

# HELP http_requests_total Total de requisições HTTP
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1234
http_requests_total{method="POST",status="500"} 7

# HELP memory_usage_bytes Uso atual de memória
# TYPE memory_usage_bytes gauge
memory_usage_bytes 536870912

# HELP http_request_duration_seconds Latência de requisições
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 100
http_request_duration_seconds_bucket{le="+Inf"} 120
http_request_duration_seconds_sum 9.5
http_request_duration_seconds_count 120
Regras do formato: # HELP = descrição humana. # TYPE = declara o tipo. Linhas sem # são samples. O endpoint padrão é /metrics via HTTP GET.

8. Limitações do Prometheus

LimitaçãoDetalheSolução
Long-term storageRetenção padrão 15 dias, storage local não escala para anosThanos, Cortex, VictoriaMetrics via remote_write
Alta disponibilidadeSem consenso nativo entre réplicas — dados podem divergirRodar múltiplas instâncias + Thanos/Cortex para dedup
Alta cardinalityMuitas time series degradam memória e TSDBEvitar labels de alta cardinality, usar recording rules
Não é para logsPrometheus é para métricas numéricas, não textoLoki, Elasticsearch para logs
100% de precisãoScrape baseado em pull — pode perder eventos entre scrapesPushgateway para eventos críticos, aumentar frequência
Dados de negócioNão adequado para dados transacionais ou billing exatoBanco de dados dedicado + exportar agregados

9. Service Discovery — Visão Geral

O Prometheus pode descobrir targets automaticamente sem precisar editar o arquivo de configuração manualmente:

static_configs
Lista manual de targets no prometheus.yml. Para ambientes simples.
kubernetes_sd_configs
Descobre pods, services, nodes e endpoints do Kubernetes automaticamente
consul_sd_configs
Integra com Consul Service Registry
ec2_sd_configs
Descobre instâncias EC2 via AWS API
file_sd_configs
Lê targets de arquivo JSON/YAML — recarrega dinamicamente

Exemplo de prometheus.yml básico

global:
  scrape_interval: 15s        # Frequência de coleta
  evaluation_interval: 15s    # Frequência de avaliação de regras

scrape_configs:
  - job_name: 'prometheus'    # Nome do job (label automático)
    static_configs:
      - targets: ['localhost:9090']

  - job_name: 'node'
    static_configs:
      - targets: ['server1:9100', 'server2:9100']
    labels:
      env: production          # Labels extras para todos os targets

Q1. Qual pilar de observabilidade é mais adequado para rastrear uma requisição lenta atravessando 6 microsserviços?
A) Métricas — por serem mais eficientes para análise de latência
B) Logs — pois cada serviço registra o evento com timestamp
C) Traces (rastreamento distribuído) com spans
D) Alertas — porque identificam o problema automaticamente
✅ Resposta: C
Distributed Tracing com spans é exatamente feito para esse cenário: rastrear o caminho completo de uma requisição através de múltiplos serviços, mostrando onde ocorreu o gargalo. Ferramentas: Jaeger, Zipkin, OpenTelemetry.
Q2. Uma empresa tem SLO de 99,9% de disponibilidade mensal. Quanto tempo de downtime é permitido?
A) 0 minutos — 99,9% significa praticamente disponível sempre
B) Aproximadamente 43,8 minutos por mês (0,1% do tempo)
C) 1 hora por mês exatamente
D) Depende do SLA com o cliente
✅ Resposta: B
Error Budget = 100% − 99,9% = 0,1%. Em um mês com 30 dias = 43.200 minutos × 0,001 = ~43,2 minutos. Este é o "orçamento de erros" disponível antes de violar o SLO.
Q3. Por que o Prometheus usa o modelo Pull em vez de Push por padrão?
A) Pull é mais seguro pois o firewall não precisa permitir conexões de entrada
B) Pull permite ao Prometheus controlar a frequência e detectar targets down (up=0)
C) Push não é suportado em nenhuma situação no Prometheus
D) Pull é mais eficiente em termos de rede
✅ Resposta: B
Com Pull, o Prometheus controla o timing do scrape e sabe exatamente quando um target parou de responder (gerando up=0). Com Push, se o agente para de enviar, não há forma simples de saber se é intencional ou falha.
Q4. Qual tipo de métrica é correto para medir o número atual de conexões abertas em um banco de dados?
A) Counter — pois conta o número de conexões
B) Summary — para calcular percentis de conexões
C) Gauge — pois o valor sobe e desce conforme conexões abrem e fecham
D) Histogram — para distribuir conexões por faixa de tempo
✅ Resposta: C
Gauge é para valores que sobem E descem. Conexões ativas aumentam quando novas conexões são estabelecidas e diminuem quando fechadas. Counter só sobe — seria correto para "total de conexões já abertas".
Q5. Qual a principal vantagem do Histogram sobre o Summary para medir latência?
A) Histogram é mais preciso — calcula percentis exatos
B) Histogram permite agregação entre múltiplas instâncias via histogram_quantile()
C) Histogram usa menos memória que Summary
D) Summary não suporta percentis acima de p90
✅ Resposta: B
Histogram armazena buckets no Prometheus e calcula percentis no servidor — por isso é possível agregar buckets de múltiplas instâncias antes de calcular o quantil. Summary calcula percentis no cliente da aplicação, impossibilitando agregação posterior.
Q6. Qual label seria problemático usar em uma métrica do Prometheus?
A) method="GET"
B) status_code="200"
C) user_id="usr_abc123"
D) region="us-east-1"
✅ Resposta: C
user_id tem altíssima cardinality — pode ter milhões de valores únicos. Cada combinação de labels = 1 time series. Isso criaria milhões de séries, sobrecarregando o TSDB. Labels devem ter cardinality baixa e previsível.
Q7. Um batch job termina em 10 segundos, mas o scrape_interval é 15s. Qual solução usar?
A) Reduzir o scrape_interval para 5s
B) Usar o Pushgateway — o job faz push antes de terminar
C) Adicionar um sleep de 5s no final do job
D) Não é possível monitorar jobs de curta duração com Prometheus
✅ Resposta: B
Pushgateway existe exatamente para batch jobs que terminam antes do próximo scrape. O job faz push das métricas (status, duração, resultado) para o Pushgateway, que fica disponível para o Prometheus scrapar indefinidamente.
Q8. Qual o arquivo de configuração principal do Prometheus e qual campo define o intervalo de scrape padrão?
A) config.yaml, campo interval
B) prometheus.yml, campo scrape_interval dentro de global:
C) prometheus.conf, campo collection_interval
D) prometheus.yml, campo evaluation_interval
✅ Resposta: B
O arquivo é prometheus.yml. O campo scrape_interval dentro de global: define o intervalo padrão de coleta. evaluation_interval define com que frequência as REGRAS (alerting/recording) são avaliadas — diferente do scrape!
