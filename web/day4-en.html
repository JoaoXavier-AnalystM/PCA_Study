1. Client Libraries - Instrumenting Your Application

Client libraries let your application expose metrics directly in the Prometheus format through a /metrics endpoint.

For the Exam

The 4 languages with official client libraries are: Go, Java, Python and Ruby. PHP and others are not official.

Python instrumentation example

from prometheus_client import Counter, Gauge, Histogram, start_http_server
import time

# Counter - only increases
REQUEST_COUNT = Counter(
    'http_requests_total',
    'Total de requisições HTTP',
    ['method', 'endpoint', 'status_code']  # labels
)

# Gauge - goes up and down
ACTIVE_CONNECTIONS = Gauge(
    'active_connections',
    'Número atual de conexões ativas'
)

# Histogram - distributes into buckets
REQUEST_LATENCY = Histogram(
    'http_request_duration_seconds',
    'Latência das requisições HTTP',
    buckets=[0.01, 0.05, 0.1, 0.5, 1.0, 5.0]  # le values
)

# Usage
REQUEST_COUNT.labels(method='GET', endpoint='/api', status_code='200').inc()
ACTIVE_CONNECTIONS.set(42)
ACTIVE_CONNECTIONS.inc()      # +1
ACTIVE_CONNECTIONS.dec()      # -1

with REQUEST_LATENCY.time():  # measures time automatically
    do_request()

# Start the metrics server on port 8000
start_http_server(8000)
# Access: http://localhost:8000/metrics

2. Naming Convention for Metrics

Following the naming convention is tested on the exam and keeps metrics consistent.

General format
namespace_subsystem_name_unit in snake_case
namespace
Application or company name. E.g., myapp, http, node
subsystem
Internal component. E.g., database, cache, api
name
What is being measured. E.g., requests, errors
unit
Unit of measurement. E.g., seconds, bytes, total
SuffixTypeExampleNever use
_totalCounterhttp_requests_total_count (reserved for Histogram)
_secondsDurationhttp_request_duration_seconds_ms, _secs (use SI)
_bytesSizehttp_response_size_bytes_kb, _mb
_ratioRatiodisk_usage_ratioPercentage (use 0-1)
_infoGauge for metadataprocess_infoMixing with real metrics
🚫 Naming Mistakes

❌ latencyMs → ✅ http_request_duration_seconds
❌ cpu_percent → ✅ cpu_utilization_ratio (0-1) or no suffix
❌ requests → ✅ http_requests_total (always a descriptive prefix)
❌ http_request_duration_ms → ✅ use seconds (SI unit)

3. Main Exporters

Node Exporter - Host Metrics

Port
:9100
Collects
CPU, memory, disk, network, filesystem, OS processes
Where it runs
Directly on the host (not in a container) for kernel access
Main metrics
node_cpu_seconds_total, node_memory_MemAvailable_bytes, node_filesystem_avail_bytes, node_network_receive_bytes_total
# CPU usage by mode (idle, user, system, iowait...)
node_cpu_seconds_total{cpu="0", mode="idle"}

# CPU usage %
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# Available memory in MB
node_memory_MemAvailable_bytes / 1024 / 1024

# Free disk %
node_filesystem_avail_bytes / node_filesystem_size_bytes * 100

cAdvisor - Container Metrics

Port
:8080
Collects
CPU, memory, network and I/O of each Docker/Kubernetes container
In Kubernetes
Already integrated into the kubelet - no separate install needed
Main metrics
container_cpu_usage_seconds_total, container_memory_usage_bytes, container_network_receive_bytes_total

Blackbox Exporter - External Monitoring

Function
Probes endpoints like an external user: HTTP, TCP, ICMP, DNS
Use cases
Check availability, verify SSL expiration, test connectivity
Differentiator
Tests from the outside - complements the application's internal metrics
# prometheus.yml - Blackbox Exporter configuration
scrape_configs:
  - job_name: 'blackbox'
    metrics_path: /probe        # blackbox's special endpoint
    params:
      module: [http_2xx]        # which module to use
    static_configs:
      - targets:
          - https://example.com
          - https://api.myapp.com/health
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox-exporter:9115  # exporter address

Pushgateway - For Batch Jobs

Port
:9091
Function
Buffer for jobs that finish before the next scrape
Push API
PUT /metrics/job/{jobname}/instance/{instance}
Delete API
DELETE /metrics/job/{jobname}
Persistence
Metrics stay until manually deleted - they do not expire
When NOT to use
For long-running services - use direct scraping
# Example: batch job pushes and deletes its metrics when done (shell)
# Push the metrics
echo "batch_job_duration_seconds 12.5" | \
  curl --data-binary @- http://pushgateway:9091/metrics/job/backup_job/instance/server1

# Push with multiple metrics
cat << EOF | curl --data-binary @- http://pushgateway:9091/metrics/job/my_batch
# TYPE batch_job_duration_seconds gauge
batch_job_duration_seconds 42.0
# TYPE batch_job_records_processed_total counter
batch_job_records_processed_total 1500
EOF

# Delete after completion (IMPORTANT!)
curl -X DELETE http://pushgateway:9091/metrics/job/backup_job/instance/server1

4. Service Discovery and Relabeling

How Service Discovery works in Kubernetes

scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod              # discovers all pods
    relabel_configs:
      # Keeps only pods with the prometheus.io/scrape: "true" annotation
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      # Uses the port from the prometheus.io/port annotation
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        target_label: __address__
        regex: (.+)
        replacement: $1
      # Copies the namespace name as a label
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      # Copies the pod name as a label
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod

Relabeling actions

keep
Keeps series where the regex matches. Drops the rest.
drop
Removes series where the regex matches.
replace
Replaces the value of a label (default action).
labelmap
Maps labels by regex - copies several at once.
labeldrop
Removes labels that match the regex.
labelkeep
Keeps only labels that match the regex.
Special Service Discovery Labels (__meta_*)

When SD discovers targets, it creates temporary labels prefixed with __meta_. These labels exist only during relabeling and are discarded afterwards. Use source_labels to read them and target_label to copy them as permanent labels.

relabel_configs vs metric_relabel_configs

ConfigurationWhen it runsWhat it affects
relabel_configsBefore scraping - filters targetsWhich targets will be scraped
metric_relabel_configsAfter scraping - filters metricsWhich series will be stored
scrape_configs:
  - job_name: 'myapp'
    static_configs:
      - targets: ['app:8080']
    # Runs BEFORE scraping - filters targets
    relabel_configs:
      - source_labels: [__address__]
        regex: '.*:8080'
        action: keep

    # Runs AFTER scraping - filters received metrics
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: 'go_.*'          # drops internal Go runtime metrics
        action: drop

Review Questions

Q1. Which exporter collects CPU, memory and disk metrics from the host operating system?
A) cAdvisor
B) Blackbox Exporter
C) Node Exporter (:9100)
D) Pushgateway
✅ Answer: C
Node Exporter runs on the host (not in a container) and exposes OS metrics: CPU, memory, disk, network, filesystem. Default port :9100.
Q2. Which language does NOT have an official Prometheus client library?
A) Go
B) Python
C) PHP
D) Ruby
✅ Answer: C
The 4 official client libraries are: Go, Java/JVM, Python and Ruby. PHP has no official library - only third-party implementations exist.
Q3. What is the correct name for a metric that counts the total number of database errors?
A) dbErrors
B) database_error_count
C) myapp_database_errors_total
D) MYAPP.DATABASE.ERRORS.TOTAL
✅ Answer: C
Naming convention: namespace_subsystem_name_unit in snake_case. Counters use the _total suffix. myapp = namespace, database = subsystem, errors = name, total = counter suffix.
Q4. What happens to metrics in the Pushgateway when the batch job that pushed them finishes?
A) They are automatically deleted after the configured TTL
B) They remain available until explicitly deleted via the API or a restart
C) They are sent to Prometheus immediately and then deleted
D) They expire after Prometheus's next scrape
✅ Answer: B
The Pushgateway persists metrics indefinitely. The batch job MUST delete its metrics when done (DELETE /metrics/job/{job}) - otherwise Prometheus will keep seeing "stale" metrics from a job that already finished.
Q5. What is the difference between relabel_configs and metric_relabel_configs?
A) relabel_configs is for Kubernetes; metric_relabel_configs is for static_configs
B) relabel_configs runs before scraping (filters targets); metric_relabel_configs runs after (filters metrics)
C) They are equivalent - just different names
D) metric_relabel_configs only works with regex
✅ Answer: B
relabel_configs: runs before scraping to decide which targets will be scraped. metric_relabel_configs: runs after scraping to filter or transform the received metrics before storing them.
Q6. What is the Blackbox Exporter for?
A) To monitor "black box" applications without source code access
B) To run external HTTP, TCP, ICMP probes - checking availability like an external user
C) To encrypt metrics in transit
D) To replace Node Exporter in containerized environments
✅ Answer: B
Blackbox Exporter checks endpoints externally: it makes HTTP requests, connects over TCP, pings via ICMP. It complements internal metrics - while the app reports internal metrics, Blackbox tests whether it is reachable from the outside.
Q7. Which relabeling action KEEPS only targets with a specific annotation?
A) action: filter
B) action: keep
C) action: include
D) action: allow
✅ Answer: B
action: keep keeps targets where the source_label matches the regex, dropping all others. It is the opposite of action: drop, which removes the ones that match.
Q8. Which exporter is recommended for monitoring pod metrics in Kubernetes with no extra installation?
A) Node Exporter
B) cAdvisor (already integrated into the kubelet)
C) Blackbox Exporter
D) kube-state-metrics
✅ Answer: B
cAdvisor is integrated into the Kubernetes kubelet - already available on every node with no extra install. It exposes CPU, memory and network metrics for each container. kube-state-metrics exposes the state of K8s objects (replicas, health), not resource metrics.
